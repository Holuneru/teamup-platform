# Ближайшие задачи TeamUp

Этот документ фиксирует следующий этап развития рабочего пространства проекта. Реализованные пункты отмечаются `[x]`; порядок оставшихся пунктов — рекомендуемый порядок работ.

## Текущее состояние

- [x] Участник открывает workspace проекта из списка проектов, где он состоит.
- [x] Владелец открывает тот же workspace из управления проектом.
- [x] Backend разрешает доступ к workspace только владельцу и текущим участникам.
- [x] Workspace содержит обзор проекта, команду и общий чат.
- [x] Общий чат сохраняет историю после выхода или исключения автора.
- [x] Уведомления не отправляются при обычных сообщениях в личном или проектном чате.
- [x] Kanban-доска содержит колонки, задачи, исполнителя, приоритет, срок и смену статуса.
- [x] Автор задачи или владелец проекта может удалить задачу.

## Этап 1. Полноценная работа с задачей

- [ ] Добавить редактирование названия, описания, исполнителя, приоритета и срока.
- [ ] Открывать подробную задачу в отдельном диалоге; ограничивать описание в карточке доски.
- [ ] Добавить комментарии к задаче и показывать их историю в подробном представлении.
- [ ] Сохранять автора и время каждого комментария.
- [ ] Проверять доступ по текущему членству в проекте для чтения и записи.

### Готово, когда

- Участник проекта может обновить задачу и обсудить ее в комментариях.
- Пользователь вне команды не может читать или менять задачи и комментарии.
- После выхода или исключения участник теряет доступ к новым данным workspace.

## Этап 2. Удобство Kanban-доски

- [ ] Перемещать карточки между колонками drag-and-drop с сохранением статуса на сервере.
- [ ] Добавить фильтр по исполнителю, приоритету и сроку.
- [ ] Добавить поиск по названию задачи.
- [ ] Показывать просроченные и ближайшие сроки заметным, но ненавязчивым маркером.
- [ ] Сохранять фильтры только в текущем просмотре, если команда не договорится о совместных фильтрах.

### Готово, когда

- Статус можно менять перетаскиванием и существующим селектором.
- Фильтры комбинируются и не меняют данные проекта.
- Карточка не теряется при обновлении страницы.

## Этап 3. Событийные уведомления

Уведомления должны помогать отреагировать на действие, а не дублировать поток сообщений.

- [ ] При назначении исполнителем уведомлять назначенного участника.
- [ ] В общем чате проекта поддержать упоминание участника через `@`.
- [ ] Предлагать в списке упоминаний только текущих участников проекта, включая владельца.
- [ ] Уведомлять только упомянутого участника; обычное сообщение без упоминания не создает уведомление.
- [ ] При новом комментарии уведомлять автора задачи и назначенного исполнителя, если это не автор комментария.
- [ ] Уведомлять исполнителя о смене статуса задачи, если изменение сделал другой участник.
- [ ] Позже рассмотреть напоминания о приближающихся сроках и просроченных задачах.
- [ ] Добавить тесты адресата, дублей, самоназначения и событий без получателей.

### Правила уведомлений

- Обычные сообщения в личном чате не попадают в раздел уведомлений; непрочитанные личные сообщения отображаются только у иконки чата.
- Обычные сообщения в общем чате проекта не попадают в раздел уведомлений.
- Упоминание `@участник` в общем чате создает уведомление только для указанного текущего участника проекта.
- Владелец проекта может быть упомянут и получить уведомление наравне с участниками.
- Бывших участников нельзя выбрать для нового упоминания; их сообщения остаются в истории.

## Этап 4. Файлы проекта

- [ ] Прикладывать файлы к проекту и/или задаче.
- [ ] Ограничить тип и размер файлов.
- [ ] Проверять членство при загрузке и скачивании.
- [ ] Продумать удаление файла вместе с проектом и политику хранения.
- [ ] Показывать имя, размер, автора и дату загрузки.

## Этап 5. Стабилизация workspace

- [ ] Проверить мобильную доску, подробности задачи, чат и загрузку файлов.
- [ ] Добавить интеграционные тесты основных сценариев владельца и участника.
- [ ] Проверить гонки при параллельной смене статуса и исключении участника.
- [ ] Перейти с периодического опроса на WebSocket только при подтвержденной необходимости.
