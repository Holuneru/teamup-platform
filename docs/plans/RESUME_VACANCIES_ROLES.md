# Резюме, вакансии и роли в проекте

План реализации продуктового потока: резюме пользователя, вакансии проектов, отклики с резюме и роли участников в проекте.

Документ рабочий: пункты отмечаются по мере выполнения. Продуктовое направление описано в [GLOBAL_PRODUCT_DIRECTION.md](GLOBAL_PRODUCT_DIRECTION.md), технические долги — в [TECH_DEBT.md](../TECH_DEBT.md).

## 1. Цель

Сделать отклик на проект осознанным:

- пользователь заполняет одно структурированное резюме и публикует его;
- владелец проекта открывает вакансии с конкретной ролью и требованиями;
- соискатель откликается на вакансию с опубликованным резюме;
- владелец рассматривает отклики по этапам и видит именно то резюме, которое было отправлено;
- принятый участник получает роль в проекте, которую владелец может изменить.

Простая подача заявки на проект сохраняется: резюме к ней можно приложить, но это не обязательно.

## 2. Согласованные решения

| Вопрос | Решение |
|---|---|
| Структура резюме | Структурированная: роль, о себе, навыки, опыт, проекты, образование, ссылки |
| Обязательные поля публикации | Желаемая роль и «о себе» |
| Количество резюме | Одно на пользователя |
| Роль проекта | Отдельная сущность «вакансия», без поля `Project.openRole` |
| Статусы отклика | `PENDING` остаётся «Новой»; добавляются `IN_REVIEW`, `SHORTLISTED` |
| Резюме в отклике | Снимок JSON на момент отправки |
| Кто видит резюме | Только владелец проекта в рамках конкретного отклика |
| Резюме для вакансии | Обязательно, только опубликованное |
| Резюме для обычной заявки | Необязательно |
| Сопроводительный текст | Необязательный, до 1000 символов |
| «Мои отклики» | Отдельная страница |
| Уведомления | Владельцу — новый отклик; соискателю — принятие/отклонение |
| Повторный отклик | Новая запись, старая не перезаписывается |
| Роль участника | Одна строка на участника, свободный текст до 100 символов |
| Автоназначение роли | Из названия вакансии при принятии отклика на вакансию |
| Обычная заявка и приглашение | Без роли |
| Редактирование роли | Только владелец, любой текст |
| Уведомление о смене роли | Нет |
| Периоды в резюме | Строка `ГГГГ-ММ` |
| Каталог вакансий | Глобальная вкладка по всем проектам |

## 3. Границы

### Входит

- CRUD резюме, черновик и публикация.
- Вакансии проекта: создание, редактирование, открытие/закрытие, удаление.
- Каталог открытых вакансий с поиском и фильтрами.
- Отклик на вакансию и обычная заявка на проект с резюме.
- Рассмотрение откликов владельцем, статусы и история решений.
- Страница «Мои отклики».
- Роли участников проекта и их редактирование владельцем.
- Уведомления по событиям отклика.

### Не входит

- Подбор кандидатов по резюме и любой AI-matching.
- Публичный каталог резюме и показ резюме в профиле.
- Несколько резюме, версии, экспорт в PDF.
- Отзыв отклика соискателем.
- Зарплата, дедлайн и автоматическое закрытие вакансии.
- Удаление аккаунта и очистка связанных данных.
- WebSocket и real-time обновления.

## 4. Модель данных

Миграции продолжают текущую нумерацию: следующая — `V8`. Стиль соответствует существующим миграциям: `BIGSERIAL`, scalar IDs, `CHECK`-ограничения, индексы. Реальные FK не добавляем — это TD-06.

| `github_url` | VARCHAR(300) | Необязательно |

| `created_at` | TIMESTAMP NOT NULL | |

`resume_experiences`

| Поле | Тип |

### 4.3. Заявки

Расширяем `project_applications`:

| Поле | Тип | Примечание |
|---|---|---|
| `vacancy_id` | BIGINT | `NULL` = обычная заявка на проект |
| `resume_id` | BIGINT | Резюме, выбранное при отправке |
| `resume_snapshot` | TEXT | JSON-снимок резюме |
| `cover_letter` | VARCHAR(1000) | |
| `updated_at` | TIMESTAMP | |

Индексы: `(vacancy_id)`, `(user_id, created_at)`, `(project_id, status)`.

Снимок сериализуется через Jackson в отдельный DTO `ResumeSnapshot` и читается обратно при выдаче отклика. Парсинг должен быть устойчив к будущим полям: неизвестные поля игнорируются, отсутствующие становятся `null`.

### 4.4. Роли участников

В `project_members` добавляется:

| Поле | Тип | Примечание |
|---|---|---|
| `position` | VARCHAR(100) | `NULL` = без роли, в UI «Участник» |

Поле `role` остаётся системным (`MEMBER`) и перестаёт выводиться в интерфейс.

### 4.5. История решений

`application_status_history`

| Поле | Тип |
|---|---|
| `id`, `application_id` | BIGSERIAL, BIGINT NOT NULL |
| `from_status` | VARCHAR(20), NULL для первого статуса |
| `to_status` | VARCHAR(20) NOT NULL |
| `changed_by_id` | BIGINT NOT NULL |
| `changed_at` | TIMESTAMP NOT NULL |

Запись добавляется при каждом изменении статуса.

## 5. API

```text
# Резюме
GET    /api/resume/me
PUT    /api/resume/me
DELETE /api/resume/me
POST   /api/resume/me/publish
POST   /api/resume/me/unpublish

# Вакансии
GET    /api/vacancies?search=&skill=&format=
GET    /api/vacancies/{id}
GET    /api/projects/{projectId}/vacancies
POST   /api/projects/{projectId}/vacancies
PUT    /api/vacancies/{id}
POST   /api/vacancies/{id}/close
POST   /api/vacancies/{id}/reopen
DELETE /api/vacancies/{id}

# Отклики
POST   /api/vacancies/{id}/apply           { resumeId, coverLetter }
POST   /api/projects/{projectId}/apply     { resumeId?, coverLetter? }
GET    /api/projects/{projectId}/applications?status=&vacancyId=
GET    /api/applications/my
POST   /api/projects/applications/{id}/review
POST   /api/projects/applications/{id}/shortlist
POST   /api/projects/applications/{id}/accept
POST   /api/projects/applications/{id}/reject

# Роли участников
PUT    /api/projects/{projectId}/members/{userId}/position   { position }
```

### Доступ

| Операция | Кто может |
|---|---|
| Своё резюме | Только владелец резюме |
| Каталог и карточка открытой вакансии | Любой авторизованный пользователь |
| Закрытая вакансия | Владелец проекта и участники |
| Создание, изменение, закрытие, удаление вакансии | Только владелец проекта |
| Список откликов проекта | Только владелец проекта |
| Свои отклики | Только сам пользователь |
| Смена роли участника | Только владелец проекта |

## 6. Правила и инварианты

1. Одно резюме на пользователя.
2. Публикация требует заполненных «желаемая роль» и «о себе».
3. Отклик на вакансию возможен только с опубликованным резюме.
4. Обычная заявка может быть без резюме.
5. Одна активная заявка на вакансию от пользователя. Активные статусы: `PENDING`, `IN_REVIEW`, `SHORTLISTED`.
6. Одна активная обычная заявка на проект от пользователя.
7. Участник проекта не может откликаться на его вакансии и подавать заявку повторно.
8. Закрытая вакансия блокирует новые отклики; уже отправленные остаются в работе.
9. Удалить вакансию можно только без активных откликов; иначе предлагается закрыть её.
10. При принятии отклика:
    - пользователь добавляется в участники;
    - `position` = название вакансии, либо `NULL` для обычной заявки;
    - остальные активные заявки этого пользователя в тот же проект переводятся в `REMOVED`.
11. Роль в проекте — свободный текст до 100 символов, `trim`, пустая строка превращается в `NULL`.
12. Владелец всегда отображается как «Владелец»; его `position` не редактируется.
13. Изменение названия вакансии не меняет роли уже принятых участников.
14. Резюме удаляется только владельцем; снимки в существующих откликах сохраняются.
15. Удаление проекта удаляет вакансии и отклики вместе с их снимками.

### Статусы

| Статус | Подпись в UI |
|---|---|
| `PENDING` | Новая |
| `IN_REVIEW` | В работе |
| `SHORTLISTED` | Шортлист |
| `ACCEPTED` | Принят |
| `REJECTED` | Отклонён |
| `REMOVED` | Снята |

Допустимые переходы:

- `PENDING` → `IN_REVIEW`, `SHORTLISTED`, `ACCEPTED`, `REJECTED`;
- `IN_REVIEW` → `SHORTLISTED`, `ACCEPTED`, `REJECTED`;
- `SHORTLISTED` → `ACCEPTED`, `REJECTED`;
- `ACCEPTED`, `REJECTED`, `REMOVED` — терминальные.

## 8. Порядок и проверки

1. Один этап — один локальный коммит.
2. После каждого этапа: `.\mvnw.cmd test` и, если менялся frontend, `npm run lint` и `npm run build` из `frontend/`.
3. Пуш — только после явного разрешения.
4. Перед коммитом обновлять документацию этапа.

Ожидаемо: тестов станет больше, этапы 1–2 дают основной прирост. Существующий набор — 51 тест.

| Риск | Как снимаем |

| `ddl-auto: update` и Flyway одновременно (TD-01) | Новые таблицы создаём миграцией до первого запуска с новыми сущностями; `CHECK` обновляем миграцией |

## 11. Связь с техдолгом

- TD-01: каждая новая миграция должна быть согласована с `ddl-auto`; после потока стоит закрыть долг полностью.
- TD-02: модели членства не трогаем, роль добавляем только в `ProjectMember`.
- TD-07: новые сервисы покрываем тестами сразу.
- TD-04: проверки прав на вакансии и отклики пишем явно и тестируем.
