# TeamUp — правила проекта

Этот документ предназначен для разработчиков и AI-инструментов, включая Cursor. Он описывает текущую архитектуру и ограничения. Перед изменением кода сначала изучайте существующие реализации и DTO; не создавайте параллельную реализацию уже имеющейся функции.

## 1. Цель продукта

TeamUp — веб-платформа, помогающая студентам находить команду для стартапов, хакатонов, учебных и исследовательских проектов. Реализованные области: аккаунты и профили, навыки, проекты/участники, заявки/приглашения, рекомендации, каталог хакатонов и каталог наставников.

## 2. Технологический стек

### Backend
- Java 21
- Spring Boot 3.5.16
- Maven
- Spring Web
- Spring Security
- Spring Data JPA / Hibernate
- Jakarta Validation
- PostgreSQL
- JWT через JJWT 0.12.6
- Lombok

### Frontend
- React 18
- Vite
- React Router
- Axios
- lucide-react
- CSS

Не заменять JWT на session authentication и не переводить Axios на Fetch без отдельной согласованной задачи: текущий проект уже использует JWT и Axios.

## 3. Архитектура backend

Ожидаемый поток:

```text
HTTP Controller
    ↓
Service (бизнес-логика)
    ↓
Repository (доступ к данным)
    ↓
PostgreSQL
```

- Контроллеры отвечают за HTTP-маршруты, чтение параметров и передачу управления сервисам.
- Сервисы содержат бизнес-правила и операции над сущностями.
- Репозитории отвечают за чтение и сохранение данных.
- Для внешнего API использовать DTO из `com.teamup.dto.request` и `com.teamup.dto.response`; не сериализовать JPA Entity напрямую.
- Использовать constructor injection; предпочтителен Lombok `@RequiredArgsConstructor`, если он соответствует стилю класса.
- Не добавлять слои, интерфейсы и абстракции без реальной необходимости.
- Сохранять единый стиль именования и обрабатывать ошибки понятным образом.

## 4. Основные пакеты

Backend расположен в `src/main/java/com/teamup`:

- `controller` — REST-контроллеры;
- `service` — бизнес-логика;
- `repository` — Spring Data репозитории;
- `entity` — JPA-сущности;
- `dto/request` и `dto/response` — контракт API;
- `mapper` — преобразование entity/DTO;
- `security` — JWT и настройки Spring Security;
- `config` — прочая конфигурация;
- `exception` — исключения и обработка ошибок;
- `enums` — enum-типы.

Frontend расположен в `frontend/src`; в нём используются страницы, компоненты, контекст, API-клиенты и стили.

## 5. Доменные области

- `User`: имя, фамилия, email, пароль, университет, курс, описание, контакты, аватар, формат участия, роль, навыки и `lookingForTeam`.
- `Skill`: уникальное имя навыка.
- `Project`: название, описание, владелец, участники, требуемые навыки и дата создания.
- `ProjectApplication`: заявка на проект со статусом и временной меткой.
- `ProjectInvitation`: приглашение пользователя в проект.
- `ProjectMember`: отдельная запись о членстве в проекте.
- `Hackathon`: описание, дедлайн, формат, место, приз и ссылка.
- `Mentor`: имя, организация, описание, контакты и навыки.

Актуальные поля и ограничения фиксируются в сущностях, а сводная модель — в [DATABASE.md](DATABASE.md).

## 6. API и frontend

- REST API документируется в [API.md](API.md).
- Не менять существующие URL, имена полей DTO и enum-значения без проверки всех frontend-вызовов и согласованного обновления контракта.
- Frontend должен использовать общий существующий API-клиент и механизм передачи JWT, если они предусмотрены текущей реализацией.
- Все видимые пользователю тексты интерфейса — на русском языке. Имена Java-классов, методов, полей, enum, URL и технические идентификаторы оставлять на английском.
- Не помещать секреты, пароли или реальные токены в код, документацию, логи или примеры. Для документации использовать placeholders.

## 7. Безопасность

- Пароли должны храниться только в виде хеша, созданного через `PasswordEncoder` (сейчас BCrypt).
- Не доверять идентификаторам пользователя из тела запроса для определения текущего пользователя. Для операций от имени текущего пользователя использовать аутентифицированный principal/JWT.
- Проверять владение ресурсом и права на каждую изменяющую операцию: JWT подтверждает личность, но сам по себе не даёт право менять любой проект, заявку, приглашение, навык, хакатон или профиль.
- Не считать роль `ADMIN` или `MENTOR` защищённой, пока проверка роли явно не реализована и не покрыта тестом.
- Не добавлять секреты в Git. Если реальный секрет уже попадал в репозиторий, вынести его в переменные окружения и заменить/отозвать опубликованное значение.
- Не отключать проверки доступа ради прохождения frontend-сценария; исправлять клиентский запрос или правила доступа.

## 8. База данных

- PostgreSQL + Spring Data JPA/Hibernate.
- Перед изменением entity проверить репозитории, сервисы, DTO и фактические запросы frontend.
- Не предполагать, что поля ID в сущности автоматически создают FK: например, в некоторых сущностях хранятся scalar IDs.
- Изменения схемы должны быть совместимы с существующими данными. Для значимых изменений сначала описать миграцию/план обратной совместимости.
- Не менять одновременно несколько механизмов членства в проекте без выяснения, как они используются.

## 9. Обязательный рабочий процесс

Перед изменением:
1. Найти текущий контроллер, сервис, репозиторий, entity, DTO и frontend-вызовы.
2. Проверить, нет ли уже такой функции.
3. Определить влияние на существующие маршруты и данные.
4. Сформулировать минимальный набор изменений.

После изменения:
1. Добавить или обновить автоматические тесты.
2. Запустить `./mvnw test` для backend.
3. Для frontend выполнить `npm run build` и `npm run lint` из `frontend/`, если изменение его затрагивает.
4. В итоговом сообщении указать изменённые файлы, поведение, проверки и известные ограничения.
5. Не утверждать, что тесты прошли, если они не запускались.

## 10. Не делать без отдельного решения

- Не переписывать проект с нуля и не заменять весь стек.
- Не удалять существующие функции ради упрощения.
- Не менять публичный API без обновления документации и frontend.
- Не добавлять Kafka, Redis, микросервисы, GraphQL или другие новые технологии без отдельного обоснования и согласования: текущая реализация TeamUp — монолитное Spring Boot-приложение.
- Не отмечать функцию как завершённую только потому, что для неё существует контроллер; нужно проверить логику и тесты.
