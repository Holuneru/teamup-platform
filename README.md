# TeamUp

**TeamUp** — веб-платформа для студентов и начинающих специалистов, которые ищут команду для стартапов, хакатонов, учебных, исследовательских и других совместных проектов.

Платформа объединяет несколько этапов командной работы: поиск людей и проектов, подбор участников по навыкам, подачу заявок и приглашения, а также инструменты для взаимодействия уже сформированной команды.

> **Состояние проекта:** активная разработка. В репозитории есть работающие функциональные модули и автоматические тесты, но покрытие тестами и отдельные части документации ещё требуют расширения. README описывает текущее состояние исходного кода, а не обещает готовность production-релиза.

## 1. Цель и концепция

Поиск команды для проекта часто происходит в разных местах: участники знакомятся в чатах, публикуют объявления, отдельно обсуждают идеи и используют сторонние инструменты для управления задачами. TeamUp стремится объединить эти процессы в одном приложении.

В основе платформы лежат три направления:

1. **Поиск и подбор.** Пользователь оформляет профиль, указывает навыки и предпочтительный формат участия. Создатель проекта описывает идею и необходимые компетенции, после чего может искать участников и просматривать рекомендации.
2. **Формирование команды.** Пользователи отправляют заявки, владельцы проектов рассматривают их и приглашают подходящих кандидатов. Участники могут принимать или отклонять приглашения.
3. **Совместная работа.** После вступления в проект команда получает рабочее пространство с доской задач, комментариями и общим чатом.

Дополнительные разделы платформы предназначены для поиска хакатонов и просмотра каталога наставников.

### Для кого предназначен TeamUp

- Для студентов, которые хотят найти команду для учебного или исследовательского проекта.
- Для участников хакатонов, которым нужны люди с определёнными навыками.
- Для авторов стартап-идей, которым необходимо собрать команду.
- Для пользователей, которые хотят представить свои навыки и находить проекты по интересам.

## 2. Возможности платформы

### 2.1. Регистрация и авторизация

В приложении реализованы:

- регистрация пользователя;
- вход по учётным данным;
- выдача JWT после успешной авторизации;
- передача токена в заголовке `Authorization: Bearer <token>`;
- защита API с помощью JWT-фильтра;
- хеширование паролей с помощью BCrypt.

После входа frontend сохраняет JWT в `localStorage` и добавляет его к запросам через общий Axios-клиент.

Текущая реализация использует stateless-аутентификацию: сервер не хранит пользовательскую HTTP-сессию. Срок действия JWT, заданный в текущем `JwtService`, составляет 24 часа.

### 2.2. Профиль пользователя

Профиль содержит информацию, которая помогает другим участникам оценить опыт и понять, подходит ли пользователь для проекта.

Поддерживаются:

- имя и фамилия;
- адрес электронной почты;
- университет и курс;
- описание пользователя;
- фотография профиля;
- список навыков;
- ссылки на GitHub и Telegram;
- предпочтительный формат участия;
- статус поиска команды.

Для формата участия предусмотрены значения:

- `ONLINE` — онлайн;
- `OFFLINE` — очное участие;
- `BOTH` — оба формата.

Пользователь может просматривать собственный профиль, открывать профили других участников и редактировать свои данные.

### 2.3. Каталог пользователей

Раздел поиска людей позволяет просматривать участников платформы и находить потенциальных коллег.

Backend поддерживает фильтрацию списка пользователей по следующим параметрам:

- университет;
- навык;
- роль;
- формат участия.

Также предусмотрен текстовый поиск пользователей. Карточки и профили помогают посмотреть основные сведения о человеке, его навыки и контактные ссылки, опубликованные в профиле.

### 2.4. Проекты

Проект представляет собой карточку идеи или инициативы, для которой автор собирает команду.

Пользователи могут:

- создавать проекты;
- просматривать каталог проектов;
- открывать подробную страницу проекта;
- редактировать и удалять собственные проекты;
- указывать название и описание;
- задавать необходимые навыки;
- просматривать владельца и участников;
- открывать список проектов, которыми владеют;
- просматривать проекты, в которых состоят;
- выходить из проекта.

В каталоге проектов предусмотрены параметры поиска по текстовому запросу и необходимому навыку.

Владелец проекта управляет составом команды. Участники получают доступ к рабочему пространству проекта в соответствии с проверками доступа на backend.

### 2.5. Заявки на участие

Заявка позволяет пользователю сообщить владельцу проекта о желании присоединиться к команде.

Основной процесс:

1. Пользователь открывает страницу проекта.
2. Отправляет заявку на участие.
3. Владелец проекта просматривает ожидающие заявки.
4. Владелец принимает или отклоняет заявку.
5. При принятии пользователь добавляется в состав проекта.

Для заявок предусмотрены статусы:

- `PENDING` — ожидает рассмотрения;
- `ACCEPTED` — принята;
- `REJECTED` — отклонена;
- `REMOVED` — участник был исключён из команды; статус используется в логике повторной подачи заявки.

Backend проверяет, что пользователь не подаёт заявку в собственный проект и не отправляет повторную заявку, пока предыдущая заявка не допускает повторное обращение.

### 2.6. Приглашения в команду

Владелец проекта может пригласить конкретного пользователя напрямую.

Получатель может:

- просматривать ожидающие приглашения;
- принимать приглашение;
- отклонять приглашение.

При принятии приглашения пользователь добавляется в команду. Повторные приглашения и попытки пригласить уже состоящего в проекте пользователя обрабатываются backend-логикой.

Статусы приглашений:

- `PENDING`;
- `ACCEPTED`;
- `REJECTED`.

### 2.7. Управление участниками

Владелец и участники проекта имеют разные возможности. Владелец отвечает за управление проектом и составом команды. Участник получает доступ к совместной работе, но не становится владельцем проекта автоматически.

В текущей реализации предусмотрены:

- просмотр участников проекта;
- просмотр рабочего пространства;
- выход пользователя из проекта;
- исключение участника владельцем проекта.

Права на конкретные действия дополнительно проверяются в backend-сервисах.

### 2.8. Рекомендации участников

TeamUp содержит алгоритм подбора пользователей под требования проекта.

При формировании рекомендаций backend:

- получает навыки, необходимые проекту;
- выбирает пользователей, у которых включён статус поиска команды;
- исключает владельца проекта;
- исключает текущих участников;
- исключает пользователей с ожидающей заявкой на этот проект;
- сравнивает навыки кандидата с требованиями проекта;
- рассчитывает процент совпадения;
- сортирует кандидатов по проценту совпадения;
- возвращает не более 20 рекомендаций.

Процент совпадения рассчитывается как доля совпавших навыков от общего количества требуемых навыков:

```text
matchPercent = matchedSkills / requiredSkills * 100
```

Например, если проекту нужны четыре навыка и у пользователя совпадают три, процент совпадения составит 75%.

Это алгоритм сопоставления по заданным признакам, а не AI-модель. Он помогает сократить список кандидатов, но не принимает решение о вступлении в команду автоматически.

### 2.9. Рабочее пространство проекта

Рабочее пространство доступно владельцу проекта и его текущим участникам. Оно объединяет инструменты, необходимые после формирования команды.

#### Доска задач

Для каждого проекта можно создавать задачи, редактировать их и отслеживать выполнение.

Карточка задачи поддерживает:

- название;
- описание;
- автора;
- исполнителя;
- статус;
- приоритет;
- срок выполнения;
- дату создания.

Исполнителем можно назначить пользователя, который входит в команду проекта.

#### Статусы задач

| Статус | Назначение |
|---|---|
| `TODO` | Задача ещё не начата |
| `IN_PROGRESS` | Задача выполняется |
| `REVIEW` | Задача ожидает проверки |
| `DONE` | Задача завершена |

#### Приоритеты задач

| Приоритет | Назначение |
|---|---|
| `LOW` | Низкий |
| `MEDIUM` | Средний |
| `HIGH` | Высокий |

#### Работа с доской

В интерфейсе предусмотрены:

- отображение задач по статусам;
- перемещение карточек между колонками;
- редактирование задачи;
- назначение и смена исполнителя;
- установка приоритета;
- установка срока выполнения;
- визуальная индикация приближающихся и просроченных сроков;
- поиск и фильтрация задач;
- фильтрация по статусу, исполнителю и приоритету;
- комментарии к отдельным задачам.

Удалять задачу может её автор или владелец проекта. Читать доску и работать с ней могут только владелец и текущие участники проекта.

### 2.10. Общий чат проекта

В рабочем пространстве проекта есть общий чат команды.

Он позволяет:

- получать сообщения проекта;
- отправлять сообщения;
- просматривать историю обсуждения.

Доступ к чату ограничен владельцем и текущими участниками проекта. Backend возвращает последние сообщения проекта. Сообщения сохраняются в базе данных, поэтому история не является только временным состоянием интерфейса.

### 2.11. Личные сообщения

Личные сообщения позволяют пользователям общаться друг с другом вне общего чата проекта.

Поддерживаются:

- список диалогов;
- открытие диалога с пользователем;
- просмотр сообщений;
- отправка сообщений;
- отметка диалога прочитанным;
- подсчёт непрочитанных сообщений;
- скрытие диалога у текущего пользователя.

Удаление диалога в интерфейсе реализовано как скрытие для одного участника. История сообщений не удаляется у собеседника.

### 2.12. Уведомления

В приложении предусмотрен раздел уведомлений.

Backend поддерживает:

- получение списка уведомлений текущего пользователя;
- получение количества непрочитанных уведомлений;
- отметку отдельного уведомления как прочитанного;
- отметку всех уведомлений как прочитанных.

Личные сообщения имеют отдельный механизм подсчёта непрочитанного. В общем списке уведомлений сообщения обрабатываются отдельно от остальных событий.

### 2.13. Каталог хакатонов

Раздел хакатонов предназначен для просмотра мероприятий, в которых пользователь может принять участие.

Карточка хакатона содержит сведения о мероприятии, в том числе:

- название;
- описание;
- дату окончания регистрации или дедлайн;
- место проведения;
- формат;
- приз;
- ссылку на регистрацию.

Backend поддерживает получение списка и отдельного хакатона, а также фильтрацию списка по формату и дате.

### 2.14. Каталог наставников

В платформе есть отдельный каталог наставников.

Для наставника предусмотрены:

- имя;
- организация;
- описание;
- контактные данные;
- связанные навыки.

Пользователь может просматривать список наставников и открывать подробную страницу отдельного профиля.

## 3. Пользовательские сценарии

### Сценарий A. Пользователь ищет команду

1. Регистрируется и входит в систему.
2. Заполняет профиль.
3. Добавляет навыки и контактную информацию.
4. Включает статус поиска команды.
5. Просматривает каталог проектов.
6. Открывает подходящий проект и отправляет заявку.
7. Следит за статусом заявки и приглашениями.

### Сценарий B. Пользователь создаёт проект

1. Создаёт аккаунт и заполняет профиль.
2. Создаёт проект с названием и описанием.
3. Добавляет требуемые навыки.
4. Просматривает рекомендации участников.
5. Приглашает подходящих пользователей или рассматривает входящие заявки.
6. Формирует команду.

### Сценарий C. Команда работает над проектом

1. Владелец и участники открывают рабочее пространство.
2. Создают задачи и назначают исполнителей.
3. Устанавливают приоритеты и сроки.
4. Перемещают задачи по статусам.
5. Обсуждают детали в комментариях и общем чате проекта.
6. Отслеживают выполнение задач на доске.

### Сценарий D. Пользователи общаются напрямую

1. Пользователь открывает профиль другого участника.
2. Начинает личный диалог.
3. Отправляет и получает сообщения.
4. Отмечает переписку прочитанной.
5. При необходимости скрывает диалог из собственного списка.

## 4. Роли и доступ

### Роли платформы

В backend определён enum `Role`:

| Роль | Назначение |
|---|---|
| `USER` | Обычный пользователь платформы |
| `MENTOR` | Наставник |
| `ADMIN` | Администратор |

Роль пользователя платформы и его положение внутри проекта — разные понятия.

### Роли внутри проекта

- **Владелец (OWNER)** — пользователь, создавший проект. Он управляет проектом и составом команды.
- **Участник (MEMBER)** — пользователь, который присоединился к проекту через заявку или приглашение.

### Проверки доступа

Защита построена на двух уровнях:

1. JWT-фильтр проверяет токен и устанавливает аутентифицированного пользователя.
2. Backend-сервисы проверяют, имеет ли этот пользователь право на конкретное действие с проектом, задачей, заявкой, приглашением или диалогом.

Например, доска задач и общий чат проекта доступны только владельцу и текущим участникам. Управлять заявками проекта может его владелец, а принять приглашение может только пользователь, которому оно адресовано.

Наличие роли `ADMIN` или `MENTOR` в enum само по себе не означает, что все административные или наставнические сценарии уже реализованы. Фактические ограничения определяются текущими правилами конкретных сервисов.

## 5. Система рекомендаций

Рекомендации реализованы в `RecommendationService`.

Алгоритм использует следующие данные:

- список требуемых навыков проекта;
- навыки пользователя;
- статус `lookingForTeam`;
- членство пользователя в проекте;
- наличие ожидающей заявки;
- наличие приглашения.

Результатом является список кандидатов с процентом совпадения и набором совпавших навыков. Если у проекта не заданы необходимые навыки, процент совпадения не рассчитывается как положительный результат, поэтому рекомендации не возвращаются.

Алгоритм не использует нейросеть и не принимает автоматических решений за владельца проекта. Окончательный выбор участника остаётся за человеком.

## 6. Архитектура приложения

TeamUp реализован как клиент-серверное веб-приложение: React frontend обращается к REST API на Spring Boot backend, который работает с PostgreSQL.

### Общая схема

```text
┌──────────────────────────────┐
│           Browser            │
│        React + Vite          │
└──────────────┬───────────────┘
               │ HTTP / JSON
               ▼
┌──────────────────────────────┐
│        Axios API Client      │
│  JWT Authorization Header    │
└──────────────┬───────────────┘
               │ REST API
               ▼
┌──────────────────────────────┐
│       Spring Boot API        │
│          Controllers         │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│           Services           │
│       Business Logic         │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│          Repositories        │
│         Spring Data JPA      │
└──────────────┬───────────────┘
               ▼
┌──────────────────────────────┐
│          PostgreSQL          │
└──────────────────────────────┘
```

Загрузка аватаров использует файловое хранилище в каталоге `uploads`, а не хранение изображения в виде поля основной таблицы пользователя.

### 6.1. Backend

Backend разделён на пакеты по зонам ответственности.

| Пакет | Назначение |
|---|---|
| `controller` | REST-маршруты, HTTP-параметры и ответы |
| `service` | Бизнес-логика и правила работы приложения |
| `repository` | Доступ к данным через Spring Data |
| `entity` | JPA-модель и сущности |
| `dto/request` | Объекты входящих запросов |
| `dto/response` | Объекты ответов API |
| `mapper` | Преобразование сущностей и DTO |
| `enums` | Статусы, роли и перечисления |
| `security` | JWT-фильтр, генерация и проверка токенов |
| `config` | Конфигурация Spring и приложения |
| `exception` | Исключения и общий обработчик ошибок |

Типичный путь HTTP-запроса:

1. Клиент отправляет HTTP-запрос.
2. Spring Security и JWT-фильтр проверяют аутентификацию.
3. Контроллер принимает параметры и DTO.
4. Сервис выполняет бизнес-логику и проверки доступа.
5. Репозиторий обращается к базе данных.
6. Результат преобразуется в DTO и возвращается клиенту.

Для внешнего API используются DTO, чтобы не связывать формат ответа напрямую со структурой JPA-сущностей.

### 6.2. Frontend

### Основные логические связи

- Пользователь может иметь несколько навыков.
- Пользователь может владеть несколькими проектами.
- Проект содержит требования к навыкам.
- Проект связан с участниками, заявками и приглашениями.
- У проекта может быть несколько задач.
- Задача может иметь исполнителя и комментарии.
- Проект может иметь историю сообщений общего чата.
- Личный диалог объединяет двух пользователей и содержит сообщения.
- У пользователя может быть несколько уведомлений.

Некоторые связи в текущей модели реализованы через отдельные сущности, а в других случаях используются идентификаторы связанных объектов. Поэтому точные типы связей, поля, ограничения и статусы необходимо сверять с entity-классами.

## 11. Безопасность и хранение файлов

### JWT и Spring Security

В текущей реализации:

- пароль пользователя хешируется с помощью BCrypt;
- JWT содержит идентификатор пользователя в поле subject;
- JWT подписывается серверным ключом;
- JWT-фильтр проверяет токен на защищённых запросах;
- при отсутствии или некорректности токена защищённый запрос не проходит аутентификацию;
- сессии Spring Security отключены, используется stateless-подход.

Маршруты `/api/auth/**` разрешены без предварительной авторизации. Остальные API-маршруты требуют аутентифицированного пользователя. Файлы, опубликованные через `/uploads/**`, доступны через настроенный resource handler.

### Важное замечание перед развёртыванием

**Текущая конфигурация репозитория предназначена для локальной разработки, а не для публичного production-развёртывания.**

В исходниках текущей версии обнаружены секретные значения, заданные непосредственно в конфигурации базы данных и в JWT-сервисе. Перед публикацией или развёртыванием необходимо:

1. Заменить и отозвать значения, которые уже могли попасть в Git.
2. Перенести пароли и ключ подписи JWT во внешнюю конфигурацию или переменные окружения.
3. Убедиться, что секреты не попадают в коммиты, логи и документацию.
4. Настроить отдельные значения для development и production.
5. Ограничить CORS разрешёнными доменами frontend.
6. Проверить права доступа на все изменяющие операции.

В README намеренно не приводятся значения паролей и ключей.

### Хранение аватаров

- Файлы загружаются через `POST /api/users/me/avatar`.
- Каталог хранения задаётся настройкой `file.upload-dir`; текущее значение — `uploads`.
- Файлы отдаются через адреса с префиксом `/uploads/**`.
- Каталог `uploads` должен сохраняться между перезапусками приложения и не должен использоваться как место хранения секретов.

```yaml
spring:

```

Укажите имя созданной базы, пользователя и пароль своего локального PostgreSQL. Не используйте реальные credentials из чужой среды и не коммитьте личные пароли.

В Windows:

```bat
mvnw.cmd spring-boot:run
```

После успешного запуска backend доступен по адресу:

```text
http://localhost:8080
```

REST API использует префикс:

```text
http://localhost:8080/api
```

### 12.5. Запуск frontend

Откройте второй терминал:

```bash
cd frontend
npm install
npm run dev
```

По текущей конфигурации Vite frontend доступен по адресу:

```text
http://localhost:5173
```

### 12.6. Связь frontend и backend

В текущем frontend API base URL задан в:

```text
frontend/src/api/axios.js
```

Сейчас используется:

```text
http://localhost:8080/api
```

При изменении адреса или порта backend необходимо обновить API-клиент. Также текущая CORS-конфигурация backend разрешает frontend origin `http://localhost:5173`; при изменении адреса frontend её нужно синхронизировать.

### 12.7. Файлы

Backend сохраняет загружаемые файлы в каталоге `uploads` относительно рабочей директории приложения. Для локального запуска убедитесь, что процесс имеет права на создание и запись файлов в этот каталог.
